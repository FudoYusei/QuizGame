Quiz
-----------------
QuizU是一个交互式问答应用程序的示例，它展示了UI Toolkit组件如何在一个小型但功能齐全的游戏中协同工作，利用各种设计模式，完成多个屏幕和游戏流管理.  

QuizU 主要是为了程序员创建的, 从开发者视角阐述了 UI Toolkit 的概念和工具. QuizU 实现了常见的设计模式和事件驱动的架构. 将它当作一个学习工具或者大型程序的启动项目.  

关键特性
-----------------

#### UI Toolkit Demos
QuizU 的设计主旨是帮助开发者轻松的理解如何使用 UI Toolkit. 该项目提供了十个小的, 易于理解的示例, 演示了 UI Toolkit 不同的方面.  

#### 带有UI管理的 quiz game
示例项目展示了一个以 UI 为中心的 quiz game. 这个项目实现了多种 UI 管理模式和 game flow. 提供了管理多个 UI Screen 以及将一个大的 UI 拆分成多个小的实操方式.  

#### Design Patterns
QuizU 展示多个核心设计模式, 包括状态机和 MVC 设计模式. 这些设计模式可以巩固游戏架构, 不被新的特性所破坏. (所谓开闭原则)  

#### Event-driven
事件驱动开发, 本项目中各个组件使用事件系统进行交流, 提升扩展和测试的低耦合性.  

UI Toolkit Demo
--------------------
demo中的场景都提供了独立的场景, 每个都作为特定 UI Toolkit 主题的展示.  

+ UXML and Visual Tree: UI Builder可视化界面中编辑的 Visual Tree, 会被转换成对应层级结构的 UXML 文件
+ Flexbox: Flexibal Box Layout Model 提供了高效的布局模型
+ UnityStyleSheets(USS): 类似web开发的css文件, 自定义样式可以重复使用, 并且可以简单的替换.
+ UQuery: 简化了在复杂层级结构中定位特定 UI Elment 的方式, 可以在 visual tree 中无缝导航特定的 UI 组件
+ Pseudo-classes: 伪类, 可以用最少的代码创建交互和动画.
+ UI Toolkit Event System: UI Toolkit 有着自身完整的事件系统
+ Manipulators: 将相关的事件抽象出来到一个单独的类中.(例如, 道具系统中的点击拖拽行为, 由mousedown mousemove mouseup三个事件组成, 并且需要维护行为产生的状态)
+ Custom Controls: 自定义 UI 控件  

SceneBootstrapper
------------------  
如果第一次打开一个陌生的 Unity 项目, 基本不知道从哪里开始, 唯一的方法就是从 Build Settings 中找到默认加载的第一个场景.  

BuildSettings 中设置的 SceneList 会在程序打包后, 默认运行第一个 Scene, 因此, 第一个 Scene 通常是引动场景, 命名为 Boot.  
但是在 Unity Editor 中, 我们可以自由打开任意一个 Scene, 进行编辑, 并直接运行打开的场景.   

SceneBootstrapper 脚本的功能:  
1. 模拟在 Unity Editor 中进入 Play Mode(点击编辑器的运行按钮)时, 从 Building Settings里默认的第一个 Scene 开始运行.  
2. 第一次启动项目时, 定位到 ReadMe
3. 提供变量切换 Load Bootstrap On Load 功能

因为 SceneBootstrapper 只是针对 Unity Editor 使用, 并且需要在 Editor 本身加载时就初始化, 所以它本身位于 Editor 文件夹中, 并且使用 InitializeOnLoad 特性.  

{% highlight csharp %}  
    /// <summary>
    /// This class auto-loads a bootstrap screen (first scene in Build Settings) while working in the Editor.
    /// It also adds menu items to toggle behavior. 
    /// </summary>
    /// 
    // This SceneBootstrapper is adapted from here:
    // https://github.com/Unity-Technologies/com.unity.multiplayer.samples.coop/blob/main/Assets/Scripts/Editor/SceneBootstrapper.cs

    [InitializeOnLoad]
    public class SceneBootstrapper
    {
    }
{% endhighlight %}  


Bootstrap Scene
-----------------  
引导场景, 作为游戏程序启动时第一个场景, 引导场景中都是游戏启动必需先加载好的 GameObject.   
各个 Manager 作为全局单例对象需要在启动时加载并且一直持续到游戏结束.  

#### Unity中的单例 

单例有很多种实现形式, 最简单的 static 修饰的静态类, 优化了初始化和解耦的依赖注入方式  

Unity Engine 的 MonoBehaviour 实例的初始化都是 Engine 代码控制的, 我们在 C# 中无法控制. 这样反而有一个隐形的好处: 在继承 MonoBehaviour 类型后, 这个类的实例保证在 Scene 加载时一同初始化.  
举例来说, 我们常用的 Awake 和 Start 方法中可以调用 Scene 中所有的 GameObject, 因为它们都在加载 Scene 的时候完成了实例化.  

单例模式需要解决的问题:  
1. 单例对象的初始化顺序, 编译器不保证静态构造函数的执行顺序, 因此想要在静态构造函数中使用别的对象可能会产生各种问题.  
2. 单例对象的生命周期, 单例对象通常都是全局可调用, 因此生命周期基本都是全局生命周期.


> ##### TIP
> [Awake 和 Start 方法的区别](https://www.cnblogs.com/guxin/p/unity-difference-between-awake-and-start-function.html)
> Awake 方法必然在场景中所有 GameObject 实例化后才会调用, Awake 方法通常用来初始化自身变量, 或者设置对于其他对象的引用   
> 在 Scene 中的 GameObject 会在全部初始化完成后, 开始调用脚本中的 Awake 方法, 但是并不保证 Awak 的执行顺序, 在 Awake方法中使用 GameObject.FindObject 可以找到场景中所有 GameObject  
> 但是如果在运行时使用 Instantiate 顺序实例化两个 GameObject A 和 B, 实例化完成后会立即调用 Awake 和 OnEnable 方法, 在 A 的 Awake 方法中无法找到之后实例化的 B.  
> Start 方法, 此时所有对象已经完成自身变量初始化, 可以调用其他对象实例方法  
> Start 方法会在 GameObject 实例化后, Awake 方法执行后, Update 方法调用前, 统一执行, 运行时实例化也是一样.  

<font color=#fbc531>不知道为什么 Awake 和 Start 的执行逻辑不一样?</font>  

#### SequenceManager
引导场景中有一个名为 SequenceManager, 顺序进行各个单例 Manager 的实例化, 注意这个顺序的含义.  
场景中的 GameObject 会跟随场景加载时实例化, 并且在场景中所有 GameObject 加载完毕后, 才开始调用 Awake 和 OnEnable 方法. 也就是说, 同一个场景中的 GameObject 可以视为同时加载完毕, 没有特定的顺序.  
<font color=#4cd137>而在运行时, SequenceManager 脚本中调用 Instantiate 来执行顺序初始化, Awake 和 OnEnable 方法的调用逻辑会有差异, 它会在每个单独的 Instantiate 方法调用完成 GameObject 的实例化后立即调用实例的 Awake 和 OnEnable 方法</font>  

这就导致了如果要在 Awake 方法中设置其他 GameObject 的引用会失败. 例如, GameObject.FindObjectWithType 来查找还没有实例化的 GameObject 会失败  

SequenceManager 持有所有 Manager 的 Prefab 引用, 并且按照顺序实例化这些 Manager  


#### DontDestroy
单例对象全局可用, 因此单例对象应该是随着程序启动就初始化, 直到程序结束才销毁  

默认情况下, Unity 以 scene 为单位统一加载 GameObject, 同时在切换场景时也会统一卸载当前场景中的 GameObjects  

Unity 提供了 DontDestroy API 来标记 GameObject 不会因为 Scene 加载/卸载操作而被连同卸载  

新建一个 DontDestroyOnLoad 脚本, 并挂载在 SequenceManager 中, 代码如下:  

{% highlight csharp %}  
    /// <summary>
    /// MonoBehaviour to preserve objects on scene loads. This can be useful
    /// for manager-level objects that need to persist over multiple scenes.
    /// If used, the user is responsible for manual cleanup using Object.Destroy.
    /// </summary>
    public class DontDestroyOnLoad : MonoBehaviour
    {
        private void Start()
        {
            DontDestroyOnLoad(gameObject);
        }
    }
{% endhighlight %}  

#### SceneLoader
第二个保证生命周期的方法是: 让新场景加载时, 保留 Boot 场景, 不销毁 Boot 场景中的 GameObjects, 以添加的方式加载场景, 并且在每次新场景加载时卸载除了 Boot 场景外的场景  

{% highlight csharp %}  
//  
// Summary:
//     Helper class to avoid paying the cost of runtime type lookups. This is also used
//     to abstract underlying type info in the runtime (e.g. RuntimeTypeHandle vs StaticTypeReg)
public class SceneLoader : MonoBehaviour
{
        // Methods

        // Load a scene non-additively
        public void LoadSceneByPath(string scenePath)
        {
            StartCoroutine(LoadScene(scenePath));
        }

        // Coroutine to unload the previous scene and then load a new scene by scene path string
        private IEnumerator LoadScene(string scenePath)
        {
            if (string.IsNullOrEmpty(scenePath))
            {
                Debug.LogWarning("SceneLoader: Invalid scene name");
                yield break;
            }
            Debug.Log("Loading scenePath: " + scenePath);
            yield return UnloadLastScene();
            yield return LoadAdditiveScene(scenePath);

        }

        private IEnumerator UnloadLastScene()
        {
            if(!m_LastLoadedScene.IsValid())
            {
                yield break;
            }

            if(m_LastLoadedScene != m_BootstrapScene)
            {
                yield return UnloadScene(m_LastLoadedScene);
            }
        }
}
{% endhighlight %}

MVP/C 模式
------------------

## 项目架构介绍 - UI层
项目使用广为流传的MVX三层架构, 这里的 X 既可以是 Controller 也可以是 Presenter 或者 ViewModel. 只要保证 Model 层和 View层分开, 业务和显示分离.  

因为, UI Toolkit 采用和 Web 开发类似的工作流, 因此下面会介绍 Web 开发的工作流模式以及本项目中使用的异同.  

### 原生的 UI 逻辑 - 后台代码
应该是从桌面开发继承而来的工作流, 每个页面对应一个后台代码类, 页面每个元素都是一个控件的概念, 页面元素在后台代码中绑定了对应的事件.Unity 原生的 UI 模式类似于后台代码.  
后台代码模式优点是: 能够快速的创建页面, 缺点是: 页面与后台代码高度绑定, 不适应于页面频繁修改的场合.  

### 常见的 MVC 结构
参考 .Net MVC 架构中, Controller 是中心, 负责接收用户输入, 调用模型层的方法, 更新视图层   
1. 通过 Url 和路由系统 , 访问 Controller 中的方法 
2. Controller 的方法返回对应的 View  
3. View 被 View Render Engine 渲染成需要的表现层  

Controller 模式需要路由系统, 根据用户请求调用对应 Controller 中的方法, 并且该方法返回 View 实例, 再经过 View Render Engine 渲染成想要的显示界面  

> #### Tip
> 
> MVC需要一个强大的路由系统和好用的ViewRender引擎, 并且制定一系列的URL规则以便可以访问到对应的方法.  
{: .block-tip}  

### 常见的 MVP 结构
MVP 结构中, View 层是中心, Presenter 是相当于 Model 和 View 的中介者. View 层抽象出交互接口  
我们可以将 Unity 引擎当作 View 层, View 层抽象出交互接口, 提供给 Presenter 作为中介者与 Model 交互.  
依赖关系存在于 View 和 Presenter 之间, Presenter 和 Model 之间   

Prensenter模式的优点是, 实现简单   

### 项目中使用的 MVP 模式  
MVP 模式 LevelSelectionPresenter, LevelSelectionPresenter 只需要专心的实现 View 层向下传递的业务调用, 以及使用 View 层的接口来驱动View层的改变  
MVP 模式的中心是 View 层, 中心层必然与 Unity 引擎的生命周期绑定, 虽然 LevelSelectionScreen 并未继承自 MonoBehaviour, 但是 LevelSelectionScreen 通过绑定事件系统实现与 Unity 引擎的生命周期的交互  

### 项目中使用的 MVC 模式
MVC 模式 SettingPresenter, 虽然名称是 Presenter, 但是实际上是 Controller.   
Controller 作为中心, 与 Unity 引擎的生命周期绑定, 因此直接继承自 MonoBehaviour, 并且通过事件系统与 View 层和 Model 层解耦  

> #### warning 
> 
> 事件系统可以解耦, 但缺点是会降低代码的阅读性, 难以找到对应的依赖关系, 可以通过 Unity Editor 扩展实现事件系统的可视化功能
{: .block-warning}
