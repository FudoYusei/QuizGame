UI Toolkit 的基础结构
-------------------------  
使用 Unity UIToolkit 进行页面开发, 基础的 UI 结构是:   
1. UI Document 页面文档, 包含显示的页面元素. 类比于 web 开发中的 html 文件
2. USS, 样式表. 类比于 web 开发中的 css 文件
3. 页面逻辑脚本. 类比于 web 开发中的 js 文件  
4. 业务逻辑脚本. web 开发中的后端代码  

#### UI Document
UI Document 在 UI Builder 中进行编辑, 然后作为 Component 附加到 GameObject 上, 跟随 GameObject 在需要时被加载  

#### USS 
USS 同样在 UI Builder 中进行编辑, 通常和 UI Document 一同, 由 UI Document 引用, 因此也跟随 UI Document 一起被加载  

#### 页面逻辑脚本
页面逻辑脚本, 负责页面交互逻辑实现以及与业务逻辑层交互  
与 web 开发的 js 一样, 通过操作页面中的 DOM 元素实现页面逻辑  
在 Unity 中, 页面逻辑类的实例初始化时, 必然需要获取一个根元素, 然后才能基于这个根元素, 操作层级中的各个 DOM 元素来实现页面交互逻辑.  

#### 业务逻辑脚本
业务逻辑脚本, 负责页面所涉及到的业务逻辑交互  
为了接触页面逻辑和业务逻辑的耦合, 会将两者分离成为独立的两个类.  
实际在页面逻辑足够简单的情况下, 页面逻辑和业务逻辑可以是一个类, 也就是所谓的后台代码架构  

MVP/C 模式  
-----------------
无论是 MVP 或者 MVC , 重点是将 Model 和 View 层分离, 即显示逻辑和业务逻辑分离.  
从实现上来讲, MVP 和 MVC 的一个明显区别就是: MVC 的中心在 Controller 中, MVP 的中心在 View 层  

之前看 MVC/P 相关知识时, 总是觉得似是而非, 这些理论知识缺了一个重要的步骤, 就是如何实现这些依赖关系, 依赖关系并不会消失, 只是会转移.  
MVC/P 其实就是将 View 和 Model 层之间的依赖关系转移到 Model/Presenter(Controller)/View 中, 以此分离 View 和 Model.  
而我们在实际开发中, 需要 MVP/C 之外一层来实例化 Model View Presenter/Controller 对象, 并且建立它们之间的依赖关系, 在不同的系统中, 当然有不同的实现.  

Unity 中的 MVP/C 结构
-------------------

Unity中实现 MVP/C 结构时, 容易让人困惑的是:  
1. 如何将 UI 层和 Unity 的生命周期融合起来
2. MVP/C 三层究竟哪一层是驱动的中心  

#### UI 层的驱动中心
之所以容易产生 UI 层与 Unity 生命周期的困惑是因为:  
在 Unity 中, 想要接入引擎生命周期太简单, 只需要继承 MonoBehaviour 即可.  
并且 UI 分为三层后, 每一层都可以继承 MonoBehaviour , 看上去三层都可以作为驱动中心, 实际上哪一层作为驱动中心都可以, 但是唯独不要每一层都作为驱动中心, 这样会导致逻辑混乱.  

UI 层本质上对业务逻辑的展示, 业务逻辑的运转自然与 Unity 生命周期紧密关联, Presenter/Controller 既然能够分离 View 的展示和 Model 的业务逻辑, 同样也可以分离 Unity 生命周期对于 UI 层的耦合  
例如, 数据初始化, 数据更新基本上都是与 Unity 引擎的生命周期相关联, 会在 OnEnable() OnDisable() Start() 等方法中进行相关操作.  

因此, 个人觉得, Presenter/Controller 作为与 Unity 生命周期结合点最为自然, 因为它能同时直接与上下两层通信, 并且可以保证 View 层和 Model 层的高内聚, 不会让 Unity 自身的逻辑侵入到 View 和 Model 层中.    

<font color=#4cd137>也可以更进一步的分离 Presenter 与 Unity 生命周期的耦合.</font>  
在 Unity 中常见的方法, 为了接触引擎与某个功能模块的耦合, 另外使用一个 Manager/Controller, 在生命周期方法内调用 Presenter 提供的方法.  

实际上, 可以看到, 每次解耦都需要额外添加第三层, 复杂度会更高, 代码可读性也会更差, 因此需要根据项目复杂程度自行取舍.  

接下来, 会从耦合性由低到高来展示例子  

SplashScreen
--------------------
SplashScreen 结构最简单  
功能: 显示加载进度条  
页面逻辑: 外部传入的进度数据显示在进度条上.  
业务逻辑: 接收业务层传递的进度数据  

可以看到, 没有复杂的页面交互逻辑和业务交互逻辑, 仅仅只是接到数据进行展示.  

LevelSelectionScreen
----------------
关卡选择界面功能很简单, 读取所有关卡信息并展示在界面上, 玩家点击选择相应的关卡进入关卡    

LevelSelectionScreen类, 使用消息系统解耦了与Presenter类的依赖, 订阅了 QuizDataLoaded 事件, 也就是加载关卡信息完毕后, 显示关卡信息在界面上  
LevelSelectionPresenter 类, 需要从 Model 层读取所有关卡信息传递给 View 层, 并且订阅 View 层的点击事件, 将选中的关卡传递给 Model 层  
因为这里交互逻辑很简单, 所以并没有抽象出对应的 IView 和 IPresenter 接口  

GameController 继承 MonoBehaviour, GameController 会在 Unity Engine 对应的生命周期方法内实例化并建立 LevelSelectionScreen 和 LevelSelectionPresenter 之间依赖关系  

Unity 中实现 MVP 结构 二
----------------
要想在 Unity Engine 的 UI 层实现 MVP 结构, 很自然的需要 UI 的执行逻辑符合 Unity Engine 的生命周期. 简单来说一定是有一个继承了 MonoBehaviour 的 Setup 类, 来建立 Screen 实例和 Presenter 实例之间的依赖关系  

以 DemoSelectionSetup 类举例, 它的主要职责就是, 在 Unity Engine 某个生命周期(通常是 OnEnable)中实例化并初始化 Screen 实例和 Presenter 实例, 并且建立它们两的依赖关系  

{% highlight csharp %}  
public class DemoSelectionSetup : MonoBehaviour
{
    private void OnEnable()
    {
        // 实例化并初始化 Screen 对象和 Presenter 对象
        // 因为这两个对象已经在 Unity Engine 的场景中实例化了, 所以通过 Editor 获取场景中已经实例化的对象
        if(m_Document == null)
        {
            m_Document = GetComponent<UIDocument>();
        }

        if(m_DemoSelectionPresenter == null)
        {
            m_DemoSelectionPresenter = GetComponent<m_DemoSelectionPresenter>();
        }

        // 实例化并初始化 Screen
        SetupDemoSelectionScreen();
    }
}
{% endhighlight %}  

这里的初始化借助了 Scene
